# Canvas3D 3D-Primitive Baseline (Phase 0b, issue #146)

Baseline performance of the **current, unoptimized** Clayground.Canvas3D 3D
primitives, recorded 2026-07-18. These are the numbers the optimized primitives
must be compared against.

## Machine / method

- **Apple Silicon Mac, Metal backend, Qt 6.11.1.**
- Measured through the **Dojo** (`claydojo`, a **QQuickWidget** render path),
  windowed (offscreen renders View3D blank).
- Instrumentation: `BenchLogger` (CSV @ 250 ms) + `PerfHud`, from
  `Clayground.Canvas3D`.
- Each step/phase runs ~8 s (churn ~10 s); the **first 2 s of every step are
  discarded** (rows before the `measure_start` note). Medians below are over the
  post-warmup rows only.
- Deterministic data: LCG `seed = 1337` (line layouts + terrain), edit RNG
  `seed = 1337 ^ 0x9e3779b9`.

### Metric caveats (important)

- **`gpu_ms` is always 0** under the Dojo QQuickWidget path (known).
- **`draw_calls` and `draw_vertices` are also always 0** here — the extended
  render stats are not populated on this path. So they are **not** usable
  baseline currency, despite the task brief. The real currency is
  **`fps`, `frame_ms`, and the CPU sub-timings `sync_ms` / `render_ms`**, plus
  the scenario-specific `build_ms` / `edit_ms` columns.
- `fps` is **display/vsync-capped** (ProMotion ~120 Hz; the continuous-rotation
  static-lines path settled at ~65 fps, the per-frame-rebuild paths reached
  ~113 fps at low load). Read `fps` as "did it keep up", and `frame_ms` /
  `build_ms` for the actual cost.
- **`MultiLine3D` has no per-line styling** — one `color` and one `width` for the
  whole batch, and a full CPU rebuild of the coords array on any change. The
  future primitive is expected to do **more** work per line (per-line color/width),
  so a fair comparison must weight that in, not just read raw fps.

## Summary tables (medians over measured window)

### 1. Lines — Static (`MultiLine3D`, N static polylines in one batch, node slowly rotated to force continuous rendering)

| N lines | fps | frame_ms | render_ms | build_ms | note |
|--------:|----:|---------:|----------:|---------:|------|
| 1 000   | 65 | 15.3 | 1.30 | 4   | trivial |
| 5 000   | 65 | 16.5 | 1.48 | 34  | |
| 10 000  | 65 | 15.7 | 1.55 | 56  | |
| 25 000  | 65 | 16.1 | 1.66 | 109 | build spike frame dropped fps to 13 momentarily |
| 50 000  | 64 | 15.1 | 2.73 | 199 | |
| 100 000 | 64 | 15.6 | 4.68 | 401 | |

**Observation:** a static `MultiLine3D` batch is GPU-cheap — even **100k**
polylines render at the vsync cap (`render_ms` only ~4.7 ms). The cost is the
**one-time CPU build of the coords array**: `build_ms` scales ~linearly, 4 ms
@1k → **401 ms @100k**. So static lines never become "unusable" on frame rate;
they become unusable on the *rebuild stall* whenever the set changes (see next).

### 2. Lines — Dynamic (`MultiLine3D`, all N lines re-set every frame — the moving/connector case)

| N lines | fps | frame_ms | render_ms | build_ms (per-frame rebuild) |
|--------:|----:|---------:|----------:|-----------------------------:|
| 100     | 113 | 6.3  | 1.12 | 1  |
| 500     | 98  | 6.7  | 1.28 | 5  |
| 1 000   | 91  | 14.8 | 1.11 | 7  |
| 5 000   | 30  | 43.1 | 1.41 | 21 |
| 10 000  | 10  | 100.7| 2.44 | 87 |

**Observation:** the **per-frame CPU coords rebuild dominates** — `render_ms`
stays ~1–2.5 ms while `build_ms` and `frame_ms` explode. Moving lines drop below
60 fps between **1 000 and 5 000** lines, are clearly unusable (~30 fps) at
**5 000**, and crawl (~10 fps) at **10 000**. (No step hit the fps<5 early-stop.)
This is the headline weakness the optimized primitive targets.

### 3. Voxel — Edit Storm (128×64×128 grid, ~73k-voxel terrain, **one `set()` per frame** at random positions)

| backend | fps | frame_ms | sync_ms | render_ms | edit_ms (per-edit set()) | one-build commit_ms |
|---------|----:|---------:|--------:|----------:|-------------------------:|--------------------:|
| static (`StaticVoxelMap`)  | **16.5** | 61.3 | 0.01 | 1.38 | **59** | 71 (at load) |
| dynamic (`DynamicVoxelMap`)| **61.5** | 15.6 | 5.91 | 3.40 | ~0 | 1 (at load) |

**Observation:** the contrast is exactly the expected one. `StaticVoxelMap.set()`
runs a **full-volume greedy remesh synchronously on every single voxel change**
(~59 ms at 128³/73k voxels → whole frame is the remesh → **~16 fps**).
`DynamicVoxelMap.set()` only marks the instance table dirty (edit_ms ~0); the
rebuild lands at render time as `sync_ms` ~6 ms, so it **sustains ~60 fps** under
the same 1-edit/frame storm. For a churning single-voxel edit load, dynamic is
~4× faster today.

> Sharp edge found while building this: `set()` calls `notifyDataChanged()`
> **per call**, so bulk-filling a `StaticVoxelMap` with `set()` triggers one full
> remesh per voxel (73k × 71 ms ≈ 86 min → it looks like a hang). The pre-fill
> must use the **batch** path (`model.fillBox(...)` + a single `model.commit()`).
> The measured runs do this. There is **no** hard size limit at 128×64×128 once
> the batch path is used.

### 4. Voxel — Churn (`DynamicVoxelMap` 30×15×30, full clear+refill every 30 ms — the VoxelDemo "wave")

| backend | fps | frame_ms | sync_ms | render_ms |
|---------|----:|---------:|--------:|----------:|
| dynamic | 36 | 29.9 | 0.32 | 1.08 |

**Observation:** at 30×15×30 (13 500 voxels) the churn is **cadence-bound, not
compute-bound** — `frame_ms` sits right at the 30 ms timer interval (~33 fps
ceiling) and it keeps up. Each cycle re-sets all ~13.5k voxels (cheap markDirty
per set) + one full instance-table rebuild + O(n) recount; that rebuild is not
yet the bottleneck at this size. Larger churn grids would expose the O(n)
rebuild — a natural extension for the optimized comparison.

## Invariants the optimized-primitive comparison MUST keep identical

- **Seeds:** LCG `1337` (line layouts + terrain heightmap); edit RNG
  `1337 ^ 0x9e3779b9`.
- **Step lists:** static lines `[1k, 5k, 10k, 25k, 50k, 100k]`; dynamic lines
  `[100, 500, 1k, 5k, 10k]`. Warmup 2000 ms, step 8000 ms.
- **Cameras (fixed, do not change):**
  lines: `pos (0, 600, 1200)`, `eulerRotation.x -22`;
  voxel-edit: `pos (0, 500, 800)`, `x -30`;
  voxel-churn: `pos (0, 120, 220)`, `x -28`.
  Static-lines node rotates `y 0→360` over `12000 ms` to force continuous render.
- **Voxel grid:** 128×64×128, `voxelSize 4`, heightmap
  `h = 2 + floor(3*(sin(x*0.08)*cos(z*0.08)+1))`; colors cycled
  `[#ff3366,#00d9ff,#ffd93d,#0f9d9a]` by `(x+z)%4`.
  Pre-fill via **batch `model.fillBox` + one `model.commit()`**; storm =
  **one `set()` per frame, NO extra `commit()`** (set already triggers the
  rebuild). Static phase then dynamic phase, 2 s warmup + 8 s each.
- **Churn:** 30×15×30, `voxelSize 5`, cycle 30 ms, 2 s warmup + 10 s measured,
  diagonal wave `h = floor(7 + 3*sin((x+z)*0.3 + t))`, `t += 0.08` per cycle.
- CSVs are written to `/tmp/clay_bench/` (out of the Dojo-watched sandbox dir —
  writing into it triggers file-watch reloads that truncate the file) and copied
  into `results/` after each run.
